프로젝트가 끝나면 규칙이 하나 남습니다

회고에 적어두고 끝내면 다음에 같은 자리에서 다시 막힙니다. 그래서 프로젝트마다 다음에 지킬 규칙 한 줄로 남기고, 실제로 다음 프로젝트에서 씁니다. 아래는 그 규칙들과, 한 프로젝트에서 다음 프로젝트로 실제로 넘어간 것들입니다.

회고에서 남긴 규칙
  • DERO
    다음에는자원 실측 → 정책(ADR) → 코드 순서로 갑니다
  • AWS 예약 서비스
    다음에는컨테이너를 2개 이상 띄우기로 결정한 그 시점에 로그 경로를 같은 그림에 그립니다
  • Lumière
    다음에는외부 터널을 쓸 때 주소를 먼저 고정하고 개발을 시작합니다
  • Bimp
    다음에는인식 기능을 붙일 때 보정 흐름을 인식 로직과 같은 스프린트에 넣습니다
  • 영화 추천
    다음에는모델을 비교할 때 평가 지표를 먼저 정하고 학습을 시작합니다
  • 멍경찰과 냥도둑
    다음에는실시간 기능에 외부 모델을 붙일 때 기능보다 응답 시간을 먼저 잽니다
다음 프로젝트로 넘어간 것
  • Lumière → DERO
    빌드와 배포가 독립 단계라는 것을 여기서 배웠고, DERO의 Jenkins 파이프라인에서 빌드 단계와 전환 단계를 처음부터 분리해 설계했습니다.
  • DERO → SnapHere
    이슈 컨벤션 · API 명세 사전 정리 · PR 리뷰를 그대로 가져왔습니다. 매번 새로 만들지 않아도 되는 상태가 된 것이 SnapHere의 출발점입니다.
  • ChADa → 이후 실험 전반
    버전을 바꿔가며 결과를 표로 남기는 방식을 여기서 익혔습니다. Bimp의 YOLO 모델링과 영화 추천의 GMF/NNMF 비교가 이 절차 위에서 돌아갔습니다.
규칙이 쌓이면 절차가 됩니다. SnapHere는 협업 방식을 새로 정하는 데 시간을 쓰지 않고 첫 주부터 기능에 들어갔습니다 — 앞의 두 프로젝트에서 만든 절차를 그대로 썼기 때문입니다.
